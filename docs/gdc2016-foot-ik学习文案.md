# GDC 2016《Fitting the World》Foot IK 学习文案

> 文档性质：基于 GDC 2016 幻灯片整理的中文学习材料，不是原始参考，不是项目规范，也不是演讲逐字稿。
>
> 原始参考：`docs/foot-placement参考参考/gdc2016-fitting-the-world.pdf`
>
> 阅读规则：文中使用“原文明确”“合理解释”“项目选择”区分信息来源。只有“原文明确”可以直接归因于 GDC。

## 一、先记住一句话

这套 Foot IK 的核心不是把脚强行贴到地面，而是提前知道脚将在哪里、什么时候接触地面，再让动画原有的脚步运动安全地运行在真实地形上方。

```text
动画决定动作的样子
预测提供修正的提前量
世界查询提供地形事实
Foot Path提供脚不能穿过的地面下界
约束系统处理锁脚、滑动和解除
髋部与转向处理维持身体平衡
```

如果只记得“向下打一条射线，然后移动脚”，就没有理解这场演讲。

## 二、作者要解决什么问题

### 2.1 复杂世界

角色需要在屋顶、斜坡、台阶、尖峰和不规则表面上自然行走。动画师不可能为每个地形高度单独制作一套动画。

### 2.2 响应式 IK 太晚

传统响应式 Foot IK 通常在当前脚底向下查询地面。脚已经快落地甚至已经穿进地面时，系统才知道目标高度发生了变化。

这会产生三个问题：

- 修正时间太短，脚突然弹向新位置。
- 脚的变化向上传递，膝盖和髋部一起抖动。
- 系统不断追赶当前地面，看起来像程序在拖动骨骼。

### 2.3 程序不能重新发明动画

动画已经包含步幅、抬脚、膝盖节奏、重心和角色风格。程序化系统如果重新生成整条脚轨迹，动作会失去原有轮廓。

因此作者在第 3 页提出三条原则：

- 原文明确：预测优于响应。
- 原文明确：保留原始运动。
- 原文明确：从生物力学中寻找约束方式。

## 三、Prediction Data 是什么

### 3.1 每只脚分别预测

第 4 页明确把预测放在每只脚上。预测需要回答：

- 下一次接触还有多久。
- 下一步会前进多远。
- 接触位置大致在哪里。
- 程序化修正可以使用多长的混合时间和多大的混合比例。

预测的价值不只是得到一个点，更重要的是得到提前量。

如果系统提前 0.3 秒知道脚会落到高台上，它可以在完整的摆动阶段逐渐抬高脚。如果系统直到接触前 0.02 秒才发现高台，只能突然把脚抬上去。

### 3.2 Prediction Data 必须自动生成

第 5 页明确说数据生成必须自动化。每个动画可能包含多次左右脚接触，每一步都有自己的时间和距离，手工标注容易漏掉、写错或随动画修改而失效。

第 6 页给出第一类接触识别方法：

- 检查脚趾高度。
- 检查脚趾速度。
- 脚趾足够低并且运动足够慢时，接触置信度提高。

第 7 页给出第二类识别方法：

- 假设脚位于地面。
- 求解腿部 IK。
- 检查位置误差。
- 检查旋转误差。
- 误差过大时，不把该姿态认作可靠接触。

合理解释：这两类过滤器用运动特征和姿态可解性共同识别 Contact 区间，减少单纯速度阈值产生的误判。

原文没有给出阈值、置信度合并公式或具体数据格式。

### 3.3 Prediction Data 不是玩家输入方向

第 9 页明确写着“使用动画的前向速度”。原文没有说用摇杆方向、期望移动方向或相机方向直接决定未来脚落点。

项目可以为了权威运动链使用 committed Body 或 KCC 世界速度，但这属于项目选择，不能写成 GDC 原话。

## 四、Predictive Character Motion

脚的预测不能脱离身体。第 9 页认为角色向前运动主要通过髋部表现，并提出：

- 使用上一个位置到预测位置之间的地面坡度。
- 髋部高度跟随这段坡度。
- 前向速度来自动画。

第 10 页的图同时画出动画位移、真实位移和平均预测地面。

合理解释：动画提供动作节奏和原始位移，真实地面决定身体最终需要被抬高或降低多少。左右脚预测地面可以共同形成身体高度参考。

原文没有给出 Future Body 的积分公式，也没有规定预测必须来自 Root Motion、KCC 还是 Gameplay Velocity。

## 五、Predictive Foot Motion

第 11 页是整套系统最关键的运动分解：

- 原文明确：左右脚分别处理。
- 原文明确：脚向前的运动来自动画。
- 原文明确：动画中的脚高度被解释成脚高于 Foot Path 的高度。
- 原文明确：最终脚不能低于 Foot Path。

可以用概念式理解：

```text
最终脚水平进度 = 动画脚水平进度
最终脚竖直位置 = 世界Foot Path高度 + 动画抬脚高度
最终脚竖直位置不得低于Foot Path
```

这里不是重新生成抬脚曲线。动画仍然决定脚什么时候向前、什么时候达到最高点、什么时候落下。

Foot Path只改变动画运行时所依附的地面基线。

这就是“保留原始运动”的实际做法。

## 六、Foot Locking 不是开关

第 13 页明确说锁脚完全由数据定义，而且不要把脚完全锁死。作者给出三种约束场景。

### 6.1 Foot Locked

- 脚位于地面。
- 位置锁定。
- 允许旋转。
- 这是最常用的状态。

允许旋转很重要。地面坡度、角色转向和腿部姿态变化都可能要求脚掌旋转。如果位置和旋转全部锁死，误差只能由膝盖和髋部承担。

### 6.2 Foot Sliding

- 脚继续贴在地面上。
- 允许小幅滑动。
- 允许旋转。
- 用于动画位置与锁定位置只有小差异的情况。

它用一点可接受的滑动换取动画轮廓和身体稳定。

### 6.3 Foot Unlocked

- 完全解除锁定。
- 优先保持平滑运动。
- 用于动画位置与锁定位置差异很大的情况。

如果误差已经过大，继续锁脚只会扭曲腿和身体。此时正确做法不是加强 IK，而是平滑解除约束。

## 七、髋部为什么会弹

第 17 页指出，髋部在坡面上会弹跳。

原因是左右脚高度不断交替。如果髋部每帧直接跟随最低脚、最高脚或两脚平均值，支撑关系一切换，目标高度也会突然切换。

作者提出：

- 定义当前支撑腿。
- 用支撑腿决定髋部高度。
- 上坡和下坡使用不同处理。
- 使用临界阻尼弹簧消除弹跳。
- 必要位移直接应用，弹簧负责增加平滑拉动。

原文没有给出弹簧公式和具体支撑腿选择算法。

项目实现时必须另外定义输入、目标、切换条件和状态所有权，不能仅凭“critical spring”几个字补出一整套算法。

## 八、脚掌朝向不是始终贴合法线

第 19 页明确提出：

- 根据移动方向调整脚的 Pitch。
- 上坡时脚更趋于水平。
- 下坡时脚更趋于与坡面平行。
- 限制 Pitch 和 Roll，因为脚旋转会拉动髋部。
- 跑步时完全关闭这套脚朝向修正。

这说明“脚底始终完全匹配地面法线”不是作者的目标。

作者优先考虑腿部可达性、人体姿态和运动速度，而不是几何上的绝对贴合。

## 九、转向为什么要靠近支撑脚

第 21–28 页讨论角色转向时的身体枢轴。

如果角色始终围绕 Entity Origin 或身体中心旋转：

- 未锁定脚会被整体旋转带着移动。
- 已锁定脚不能跟着移动。
- 腿被迫吸收两个空间之间的差异。
- 最终产生脚穿透、腿扭曲和身体失衡。

作者把旋转中心移到接触脚附近：

- 接触脚因旋转产生的位移更小。
- 接触脚保持位置锁定，但仍可旋转。
- 摆动脚继续沿 Foot Path 移动。
- 身体更接近真实的踩脚转身。

这一段属于 Foot Lock 和身体转向阶段，不是 Landing Prediction。

当前项目如果还只验证预测落点，就不应把接触脚 Pivot 或未来 Yaw 外推提前塞进 Landing 查询。

## 十、为什么两个正确落点仍会穿地

第 29 页列出三类问题：

- 小障碍。
- 台阶和尖峰。
- 无法通过的高差。

即使当前落点和未来落点都正确，两点之间的直线仍可能穿过障碍。

```text
起点有效 + 终点有效
不等于
中间路径有效
```

因此作者继续引入 Virtual Ground 和 Ground Envelope。

## 十一、Virtual Ground

第 30 页展示右脚、左脚、右脚的交替接触，并提出在对侧脚接触位置拆分 Foot Path。

这样做有两个目的：

- 模拟人体把支撑从一只脚转移到另一只脚。
- 使用中间支撑点帮助路径越过尖峰。

“每只脚独立”与这里并不矛盾。每只脚的运动和约束可以独立求解，但仍可读取对侧脚接触作为路径参考。

Virtual Ground 是作者在完整 Foot Motion 中使用的概念。它是否需要进入当前项目，应根据后续摆动脚问题决定，不能仅因为原文出现就立即建立一个空模块。

## 十二、Ground Envelope

### 12.1 为什么只查落点不够

第 32 页展示屋顶场景：

- 当前落点位于凸起一侧。
- 未来落点位于另一侧。
- 两个落点都没有看到顶部。
- 两点直线从屋顶凸起内部穿过。

Ground Envelope的目标是检测两步之间的表面，并生成脚不能穿过的连续路径。

### 12.2 Ground Detection

第 33 页明确写着：

- 沿 Foot Path 使用 Capsule Cast。
- 查询得到表面位置。
- 查询得到表面法线。

Capsule在这里表示地面路径采集范围，不表示真实鞋底形状。

原文没有规定：

- Capsule必须等于脚掌大小。
- 使用矩形或四角Sole查询。
- Capsule的半径和长度。
- 是否分段执行Physics查询。
- Landing必须使用SphereCast。

这些都属于项目选择。

### 12.3 Ground Path

第 34 页明确给出四步：

1. 从近到远排序。
2. 从低到高排序。
3. 验证法线。
4. 定义Edge Planes。

Capsule可能同时命中斜面、竖直台阶面和顶部。同一路径位置可能存在多个高度和不同法线，因此需要稳定地恢复表面次序。

合理解释：接触位置和法线可以定义局部表面平面，相邻平面的关系可以帮助推导台阶或尖峰边缘。

原文没有给出法线阈值、平面求交公式、去重规则和候选身份。

### 12.4 Reachability

第 35 页要求：

- 检查所有Edge的竖直距离。
- 标记大的高度变化。

它用于区分脚能跨过的地形变化和无法通过的高差。

第 31 页写的是“移除不可通过点”，第 35 页写的是“标记大的变化”，第 37 页展示的是“Invalid Segment”。

原文没有规定：

- 整条Envelope必须失败。
- 只删除单个候选后继续。
- 必须发布某个typed rejection。
- Gameplay角色移动必须因此被阻止。

具体失败语义必须由项目自己设计，并明确标成项目选择。

### 12.5 Convex Hull

第 36 页明确要求：

- 使用Convex Hull。
- 得到连续路径。
- 只服务脚部。

图中的最终路径位于障碍上方，避免脚沿凹陷或直线切入几何内部。

原文只写了Convex Hull，没有明确写二维投影、上侧单调链、共线点规则或数值容差。

把接触投影到“前进方向 + Up”的二维平面并计算上侧Hull，是合理工程实现，但仍然属于项目选择。

“Feet only”表示Ground Envelope只用于脚部防穿透和摆动路径，不是导航路径，不是角色胶囊，也不直接替代KCC世界可达性判断。

## 十三、完整数据链

按照演讲逻辑，可以把整套方法还原为：

```text
动画资产
-> 自动分析左右脚Contact、Delay、Distance和约束区间
-> 运行时预测下一次脚接触的时间与位置
-> 预测身体运动与平均地面
-> 查询两次接触之间的地形位置和法线
-> Ground Path排序、法线验证与Edge
-> Reachability
-> Ground Envelope
-> 动画提供脚的水平进度和抬脚高度
-> Locked / Sliding / Unlocked约束脚
-> 支撑腿与髋部弹簧稳定身体
-> 脚朝向和接触脚Pivot处理坡面与转向
-> IK Solver把目标落实到最终Pose
```

这里的IK Solver只是最后执行目标的工具。文章大部分价值都发生在Solver之前。

## 十四、GDC没有定义的东西

以下概念不能归因于这篇GDC：

- Ground Path Plan。
- Ground Path Revision。
- Revision冻结和跨帧复用。
- Committed/Pending双页。
- Query generation、request identity和typed rejection。
- FinalIK、FBBIK、LegIK或TwoBoneIK。
- Unity Physics的具体API组合。
- Landing SphereCast。
- Future Body Yaw外推。
- 网络、Rollback和确定性状态。

这些能力可能在项目中有用，但必须用项目自己的业务问题来证明，不能因为“看起来专业”就放进架构。

## 十五、与当前项目的关系

当前项目可以把文章拆成逐步可观察的阶段：

```text
第一阶段：Step + Future Body -> Raw Landing -> Landing Query
第二阶段：两次Accepted Landing -> Ground Detection
第三阶段：Raw Contacts -> Ground Path -> Reachability -> Ground Envelope
第四阶段：Animation Foot Motion + Ground Envelope
第五阶段：Foot Constraint / Foot Lock
第六阶段：Pelvis、Orientation与Turn Pivot
第七阶段：唯一FullBodyIK落实Goal
```

每一阶段只验证自己的输入和输出，不应提前建立后续阶段的空数据结构。

当前Landing阶段不需要Revision。Ground Detection也不因为需要缓存就自动变成一个领域Revision。若异步查询需要防止旧结果回写，可以使用通用request generation；那是基础设施，不是GDC Foot IK算法。

## 十六、常见误解

### 误解一：预测点应跟随输入方向

不准确。GDC明确使用动画前向速度。项目如果使用Body/KCC速度，是权威运动适配，不是输入方向预测。

### 误解二：Foot Path就是两个落点之间的直线

不准确。直线可能穿过中间障碍。Ground Detection、Ground Path和Ground Envelope正是为了解决这个问题。

### 误解三：Capsule代表真实脚掌

不准确。它是路径采集包络。原文没有要求它等于鞋底尺寸。

### 误解四：Convex Hull就是完整Foot IK

不准确。Hull只生成连续地面下界。动画抬脚、约束、髋部、朝向和最终Solver仍然在后面。

### 误解五：Locked就是脚完全不能动

不准确。作者最常用的Locked状态仍允许脚旋转。

### 误解六：Ground Envelope决定角色能不能走过去

不准确。作者明确写了Feet only。Gameplay/KCC可达性是另一层职责。

## 十八、最终记忆卡

```text
预测不是猜输入，而是提前获得接触时间和位置。
动画不是被替换，而是被放到真实Foot Path上方。
锁脚不是一个开关，而是多个约束状态。
髋部稳定依赖支撑腿和弹簧，不是两脚高度平均。
落点正确不代表中间路径安全。
Capsule采集地形，Ground Path整理地形，Envelope生成连续脚部下界。
Convex Hull只服务脚，不负责Gameplay移动。
Plan和Revision都不是这篇GDC定义的Foot IK步骤。
```
