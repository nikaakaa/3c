# 可琳渲染数据总览

这份表以原磁盘资源、已有 dump 和原程序绑定表为准。截图只看外观，课件只辅助理解，不用于填原始参数。

## 怎么看

- **先看本页**：数据分哪几类，哪些已经读到，项目还差什么。
- **查具体参数**：[参数明细](参数明细.md)。包含默认声明、材质值、全局值、角色缓冲和项目绑定。
- **查完整精度与出处**：[整理数据.json](整理数据.json)。保存原字段、原字节、来源文件、哈希与读取地址。

目前整理范围是“可琳角色渲染已有证据”，不是整个 ZZZ 的所有数据。下方 33 份来源与明细保留整理当时的固定快照；后续描边接入的新数据与实际验收见 [原描边报告](../Archive/Records/ZZZ-原描边接入与验收-20260906.md)，不混改原快照数值。

## 2. 先分清四种来源

| 标签 | 是什么 | 可以证明 | 不能直接证明 |
| --- | --- | --- | --- |
| 原磁盘资源 | 材质、纹理、Shader 声明与字节码 | 文件保存了什么、程序有哪些输入和计算 | 某次绘制实际启用了哪个分支 |
| 829 快照 | 旧会话的全局参数缓存 | 那份缓存中已经发布的值 | 所有场景恒定用这些值；与 0905 同一帧 |
| 0905 物理快照 | `ZZZ_20260905_101643.raw` 中的对象、数组、CPU 缓冲 | 对象关系、该内存位置保存的值 | 所有对象处于同一次更新；GPU 最终颜色已读回 |
| 项目观测 | 3C 的 audit 和相机输出 | 我们的实现当前实际做了什么 | ZZZ 原实现一定相同 |

**“已读到值”不等于“已证明完整机制”。“值为零”不等于“游戏永远关闭”。**

0905 文件大小为 36,507,222,016 字节，CR3=`0x62DF6A000`。本轮只按已确认地址读取少量数据，没有读运行中的游戏，也没有重新全量扫描。

## 3. 原色、材质、场景输入，分别管什么

```text
原贴图和材质参数
  决定：可琳本来的颜色、分区、金属和高光特性
             ＋
每个角色的数据
  决定：角色位置、头部方向、实体索引等
             ＋
场景和相机输入
  决定：主光、环境光、阴影、调色、投影等
             ↓
原 Shader → 专用缓冲 → 角色合成与后处理
```

GI 是间接光，不是所有颜色变化的总称。主光、环境光、阴影和 LUT 调色是不同输入；整理时不把它们混成一个“场景 GI 参数”。

## 4. 可琳使用的原资源

| 部位 | 原 Shader | 主要纹理或输入 |
| --- | --- | --- |
| Body / Body02 | NapAvatarStandard | Body D/N/M/A、MatCap、全局 Overlay |
| Hair | NapAvatarStandard | Hair D/N/M/A、全局 Overlay |
| Weapon | NapAvatarStandard | Weapon D/N/M/A、全局 Overlay |
| Face | NapAvatarStandardFace | Face D、Female_Face_Lightmap、头部矩阵 |
| Eye | NapAvatarStandardEye | Face D、面部明暗图、Eye_E |
| HairShadow | NapStencilShadowCaster | 专用几何和 stencil 遮罩 |

Body/Body02 共用 Body 材质。Face 原模型有两个子网格，分别使用 Face 和 Eye，不是额外拼了一份社区眼睛。

### 关键贴图通道

| 贴图 | 原程序中的作用 | 注意事项 |
| --- | --- | --- |
| D | 原色 | D 图是 sRGB；不要当作线性数据图导入 |
| N 的 RG | 解码切向法线 | N 的 B 另参与明暗偏移，不是直接拿整张 RGB 当普通法线 |
| M 的 R | 选择五组材质参数 | 序号不天然代表头发、衣服或金属，必须结合该角色贴图 |
| M 的 G / B | 金属度 / 高光相关遮罩 | 材质里 Metallic=1 不等于整个角色全是金属 |
| A 的 G / B | 平滑度相关输入 / MatCap 遮罩 | 某些通道在特定分支才使用，不把“此图没信息”推广成“程序永远不用” |
| CharacterOverlayTex | `max(原色 + Overlay - 0.5, 0)` | 全局线性纹理；不是 MatCap 的 Overlay 混合模式 |

### 不需要猜的几个材质值

| 参数 | Body | Hair | Weapon |
| --- | ---: | ---: | ---: |
| `_UseOverlayTex` | 1 | 1 | 1 |
| `_OverlayTexScale` | 50 | 30 | 30 |
| `_Metallic` | 1 | 1 | 1 |
| `_Glossiness` | 1 | 1 | 1 |
| `_OutlineWidth` | 1 | 1 | 1 |

Body 有 `_MATCAP_ON` 关键字；Hair 的原保存关键字为空。不能因为两者都有 MatCap 参数槽，就认为两者一定启用了同一变体。完整色值和五组分区参数见明细第 2 节。

## 6. 可琳自己的对象与参数缓冲

已定位的可琳实体地址：`0x7005F028640`。

| 对象缓存字段 | 0905 中的实际值 |
| --- | --- |
| MiddlePointTransform | `0x70058A31D60` |
| HeadBone | `0x70058A31D40` |
| MiddlePointPosition | (2.957372, 13.200518, -4.922901) |
| HeadBonePosition | (2.921817, 13.516609, -5.170075) |
| HeadBoneForward | (-0.266504, -0.270337, -0.925145) |

这类位置是**那一场景中的坐标**，不能直接填给当前 Unity 场景。

同实体的 NapCB 读取链已核验：

```text
NapRenderEntity
  → NapCBWrapper：0x7005EF7A2C0
  → VectorArrayBuffer：0x7005EFCD9F0
  → CPU Vector4 数组：0x7005EF46640
  → 41 × 16 字节
```

例如 `_PackedParams1=(0,0,0,1)`、`_EntityInfo=(0,1,0,0)`；头部矩阵行和环境渐变参数也保留在明细中。

数组第 0 组读到 `(2.980336,13.200904,-4.921577,1)`；本次汇集的原绑定表没有命名该槽，保留组号，不用相似数值替它补业务名。对象缓存与该数组不能未经时序核对就当作同次提交。

## 7. 两条不能冒认成可琳的光照记录

原管理器准备列表里读到两条 208 字节记录，但其对应实体均未取得：

| 记录 | Position | Head/Face 特征 | 当前裁决 |
| --- | --- | --- | --- |
| 0 | (5.159296, 13.200221, -5.739339) | 有方向和位置数据 | 保留原值；不指定为可琳 |
| 1 | (4.067405, 12.590419, -5.383866) | 方向和位置含 (-1,-1,-1) | 保留标记；不当正常头部向量 |

**不能因为第一条“看起来有效”，就拿它代表可琳的最终灯光。** 原 GPU 输出结构布局和 CPU 输入列表是两种证据；快照里 D3D11 Buffer 没有已取得的 CPU 像素/数据镜像，不能用项目 GPU 读回代替游戏 GPU 结果。
