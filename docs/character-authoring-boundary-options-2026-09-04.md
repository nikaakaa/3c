# 角色作者与执行边界：BTSMTL、代码和 Canvas 方案对比

日期：2026-09-04。本文件是建议与取舍记录，不是已批准的迁移计划；没有修改当前代码、资产、主 spec 或已有 change。能力事实与源码清单见[Canvas 能力核对](D:/Unity_Project_1/3C/docs/canvas-capability-assessment-2026-09-04.md:1)。本轮补查了导入版 Canvas 的运行调试、单步、断点和保存入口，没有启动 Unity 或执行 Player 验证。

**建议边界：角色每 Tick 的规则与状态以明确代码模块承担；动作时间、曲线和资源关系保持数据化与可视化编辑；Canvas 可以承担高层 AI／流程编排；完整角色预览由正式场景与 Session 统一管理。现有 Program 是否继续承担运行数据，和作者使用代码、BTSMTL 或 Canvas，应分别决策。**

**1．代码、图和数据各负责什么。**

| 模块 | 输入 | 输出 | 建议所有者与原因 |
|---|---|---|---|
| 输入接入 | 玩家操作、AI 意图、网络时序与身份 | 正式输入值和带身份的动作请求 | 现有 Control Source／Session 入口；统一处理序号、Tick、缓冲和来源 |
| 角色规则 | 正式输入、角色状态、动作配置 | 本 Tick 的动作决定、移动需求及后续提交候选 | 明确 C# 业务模块；方便检查准入、打断、退出顺序和状态归属 |
| 世界与数值求解 | 正式世界请求、Body／World 状态 | 求解后的 Body／World 候选 | 当前 World／KCC 模块；热点可按实际测量使用 Native／Jobs／Burst |
| 动作内容 | 动画引用、窗口范围、曲线、Warp／Cue 配置 | 经过验证的动作运行数据 | 专门的动作资产和 Timeline 编辑器；保留作者看时间与动画的优势 |
| 姿态表现 | 已提交 Body／动作事实与表现输入 | 姿态、骨骼、相机和表现事件 | 当前 Pose／动画／IK 模块；不由普通图节点分散写骨骼 |
| AI／上层流程 | 正式观察、目标与任务配置 | 移动意图、动作请求、流程决定 | 可用 C# 或 NodeCanvas；使用哪种作者形式不改变角色请求入口 |
| 作者工具 | 正式作者资产与编辑命令 | 修改后的同一份资产及错误定位 | BTSMTL 专用界面或选定 Canvas 前端；每类作者数据只有一个真来源 |
| 预览与诊断 | 场景配置、正式产物、输入、已提交事实 | 真实角色试验、图内观察和诊断记录 | 正式场景／Session 生命周期；窗口只请求控制和显示事实 |

这些是所有权边界，不要求创建同名新类。角色管线当前已经主要由 C# 执行，BTSMTL 负责作者数据并编译到 Program。不能把当前情况误写为每帧直接运行 BTSMTL 作者对象；因此更换作者形式不会自动提高现有 KCC 或 Pose 求解速度。

玩家视角的“攻击成功”必须来自角色正式结果。Canvas 的任务 Success、FSM 状态名或 Blackboard Bool 只能表达插件自己的运行过程，除非通过明确业务合同与正式结果关联，不能成为第二份 Action 真值。

**2．优化边界。**

- 高频状态更新、数值求解、批量姿态和碰撞处理，保持预分配、明确状态和可测量的调用链。是否需要 Burst 或原生批处理，由实际 Player 热点决定。
- 图中的一个“提交攻击请求”可以是粗粒度调用；将大量每骨骼计算、每碰撞迭代或跨帧求解残差拆成普通 Flow 节点，会增加边界和调试成本。
- C# 同样可能分配、装箱、错误调用 Unity 时间或隐藏状态；代码形式本身不是性能和确定性的保证。
- 当前 Program 的索引、状态布局与正式产物可以有独立价值；无需为了转向代码作者先把这些正确实现全部删除。
- 代码作者有两种不同迁移：C# 构建器生成原运行数据，或 C# 业务模块直接成为正式规则执行者。前者保留 Program 构建成本，后者涉及更大执行合同变化，不能混称为“改成代码”。

**3．网络边界。**

网络层负责收集、排序、传输、确认和校验输入／状态身份；角色规则只通过正式输入进入现有 Session。网络 Handler、NodeCanvas Task、FlowCanvas 方法节点和预览窗口都不取得额外 Body／Action 写入权。

对参与预测、纠正和回滚的逻辑，影响未来 Tick 的变量、等待进度、状态机位置及随机状态必须被正式恢复机制覆盖。把它们藏在 C# 协程、闭包或 Canvas Task 私有字段中，都有同样的问题。

NodeCanvas 若只运行在权威端，产生的正式输入可由客户端／回放消费，客户端不一定需要再次运行同一棵 AI 树。业务收益是减少客户端 AI 同步负担；代价是只重放输入时不能还原 AI 为什么作出决定，AI 调试可能还需记录观察与决策。如果需要服务器本身回滚 AI 决策，插件内部状态依然需要恢复方案。

当前 AICharacterControlSource 已有 CaptureState／RestoreState，迁移时不能默认删除。当前普通 .NET Host 也不能直接运行依赖 Unity 的 Canvas 图；“权威端用 Canvas”需要确认它是 Unity Authority 宿主，还是普通 .NET 宿主。依据：[当前 AI 输入与状态入口](D:/Unity_Project_1/3C/3cDemo/Client/3C_Client/Assets/GameScripts/Main/Runtime/Character/AI/AICharacterControlSource.cs:131)。

**4．热更新边界。**

| 内容 | 建议采用边界 | 业务取舍 |
|---|---|---|
| 数值常量、动作窗口、曲线和资源引用 | 版本化内容；通过正式校验后在定义的边界采用 | 迭代快；影响玩法的数据仍需参与会话版本校验 |
| 业务规则或自定义 Task／Node | 明确热更程序集与输入／状态合同 | 可以修改行为实现；需要处理 AOT 泛型、引用、类型缓存及旧实例退出 |
| 高频数值与 Native／Burst 求解 | 稳定 AOT 实现，通过数据和窄接口驱动 | 易于优化与复用；算法实现变化通常涉及重新发布对应可执行内容 |
| 运行中的行为或状态布局 | 不默认无损替换；明确角色／动作／会话切换点 | 保持状态可解释；战斗中不断流升级属于额外迁移能力 |
| 联网对局采用新规则 | 由正式会话身份统一决定版本 | 避免双方各自更新造成结果差异；限制任意时刻单端修改 |

基础接口与稳定实现放 AOT，适合频繁改动的策略放热更代码或数据，是一种可选分工；并非要求把整个角色核心都挪进 GameLogic。热更代码也不应被默认视为具有与 AOT 相同的 Burst 编译产物。HybridCLR 的实际限制应按采用版本验证，参见[官方 FAQ](https://www.hybridclr.cn/en/docs/help/faq)。

BTSMTL 编译出数据不妨碍数据更新；C# 能热更也不代表任何时刻可以替换存活状态；Canvas Live Edit 更不代表已发布 Player 的热更和状态迁移已经闭合。三个选择都需要共同的版本、装载、验证和采用流程。

**5．AI 时代代码作者与图作者的取舍。**

对主要由程序员与 AI 协作维护的复杂规则，C# 的文本差异、符号引用、批量修改与静态检查有直接价值。角色准入／打断／退出等控制规则可以优先按业务代码模块设计，而不强制拆成通用节点。

时间窗、动画对应关系、曲线形状和 Pose 拓扑，仍有可视化作者价值。让 AI 写所有时间数字，并不能替代人观察动作手感和时间关系。建议保留专用 Timeline／Pose 作者表面，不把它们一并视为不必要的通用蓝图。

现有 Agent Document v4 已提供结构化作者入口，所以“AI 不能编辑图”不是当前项目的事实。真实取舍是：继续维护 Document／Reconciler／source map 的成本，能换来多少人类作者与 AI 共用的编辑收益。

若“UE 把蓝图视为不更新”指停止维护，没有查到支持这一说法的官方依据。Epic 当前 UE 5.8 文档仍明确讨论并推荐 C++ 基础与 Blueprint 的合理组合；其理由包含运行成本、表达复杂度和团队分工。若所指是发布后的代码热更，则应与 Editor 作者迭代分开讨论，不能据此推出停止维护。参见[Epic：Blueprint 与 C++ 的分工](https://dev.epicgames.com/documentation/en-us/unreal-engine/coding-in-unreal-engine-blueprint-vs-cplusplus)。

这个外部事实不要求本项目开发通用蓝图。对本项目是否值得做，仍应看具体作者和运行需求。

**6．Canvas 的“预览”实际是什么。**

| 能力 | 本地源码或官方文档结果 | 对当前预览方案的意义 |
|---|---|---|
| 执行节点高亮、状态、运行时间 | 有 | 可直接观察其自身图实例 |
| Flow 执行线和数据值观察 | 有 | 便于排查事件和方法调用 |
| 图的开始／停止／暂停／单步 | 有，要求 Play Mode 和目标 Owner | 控制图行为，不自动同步世界、角色与动画 |
| 断点 | 有；部分路径使用 Debug.Break | 可能暂停本 Unity Editor，不会因此暂停远端服务或其他进程 |
| Play Mode 中编辑图 | 官方明确支持 | 需要区分改的是运行实例、Bound 内容还是资产 |
| 保存运行中的图 | 有 Save To Asset 等入口 | 当前代码是创建新资产并复制序列化内容，不等于按现有项目要求更新原作者资产 |
| 角色预览场景、起始条件、正式输入与完整重建 | 未提供本项目对应实现 | 仍由项目的场景预览工作流负责 |
| 完整 Session 单 Tick 推进 | 未发现 | 需要正式运行宿主协调，不能用图单步替代 |
| 任意时间定位并恢复 Gameplay／物理状态 | 未提供通用能力 | 需要完整状态恢复与受控重演；移动编辑游标不代表世界已恢复 |
| 观察现有 compiled Program 的节点状态 | 不自动支持 | 仅借 Canvas 编辑器时，需开发 Program 到图的只读调试映射 |

关键源码：[GraphEditor.ShowPlaymodeGUI](D:/Unity_Project_1/3C/3cDemo/Client/3C_Client/Assets/ParadoxNotion/CanvasCore/Framework/Design/Editor/Windows/GraphEditor.cs:1286) 在单步按钮中只调用 PauseBehaviour 和 UpdateBehaviour。[GraphOwner.UpdateBehaviour](D:/Unity_Project_1/3C/3cDemo/Client/3C_Client/Assets/ParadoxNotion/CanvasCore/Framework/Runtime/Graphs/GraphOwner.cs:241) 调用无参数 UpdateGraph，其默认时间仍来自 Unity。它没有调用项目 Session 的统一输入、World Solve 与 Presentation 事务。

[Save To Asset](D:/Unity_Project_1/3C/3cDemo/Client/3C_Client/Assets/ParadoxNotion/CanvasCore/Framework/Design/Editor/Windows/GraphEditor.Toolbar.cs:205) 创建新 Graph asset 并 CopySerialized。它不能自动满足原预览提案中的“运行中修改正式作者值、保留 Undo、显示运行采用结果、退出 Play 后保留修改”全部要求。

官方介绍对应的是运行时图调试：[NodeCanvas Visual Debugging](https://nodecanvas.paradoxnotion.com/documentation/?section=visual-debugging)、[FlowCanvas Visual Debugging](https://flowcanvas.paradoxnotion.com/documentation/?section=visual-debugging)。

因此不论作者选哪条路线，建议统一为：预览场景经正式启动器创建 Session → 注入正式玩家／AI／录制输入 → 正式角色和世界执行 → 作者窗口、Canvas 窗口与诊断只读观察。暂停、单步、重建由一个明确宿主管理。素材曲线和单 Clip 编辑可以继续使用各自合适的工具，不要求拥有另一套完整角色运行器。

**7．同级方案比较。**

| 比较项 | A：继续 BTSMTL，收窄其职责 | B：角色规则转代码，保留专用动作数据编辑 | C：Canvas 接管通用编排，自研领域实现 |
|---|---|---|---|
| 作者主要操作 | Graph／FSM／Timeline，复杂数学留代码 | 修改规则代码，编辑动作数据／时间／曲线 | 配置 BT／FSM／Flow，领域能力通过任务提供 |
| 主要收益 | 复用当前资产、Program、Document 和来源追踪 | 减少通用图规则与映射维护，文本协作直接 | 复用现成编排、图工具与其运行诊断 |
| 优化 | 当前编译运行边界保持，优化实际执行热点 | 更直接检查与组织规则；仍需控制分配和状态 | 粗粒度编排通常可行，热点留领域代码；插件调用成本需测 |
| 网络 | 现有状态与数值合同迁移较少 | 状态恢复与网络合同必须继续落实到代码状态 | 插件的隐藏运行状态不是现成快照，等价迁移成本较高 |
| 热更新 | 更新运行数据／产物，新增语义另走代码发布 | 规则代码与数据可分别发布，仍需会话版本和状态边界 | 图数据更新方便，新 Task 走代码热更，运行中切换仍需设计 |
| 预览 | 已有作者／诊断关系可复用，场景预览仍需完成 | 图内高亮减少，需要清楚的业务状态与时间诊断 | 自身图调试现成；完整角色预览与原 Program 观察仍不自动具备 |
| 保留的自研内容 | 专用作者工具、编译、动作与执行 | 角色核心、动作内容工具、必要运行计划与诊断 | 角色业务、动作 Timeline、请求／观察接口、网络与诊断接入 |
| 主要代价 | 继续承担作者框架维护，必须限制通用化范围 | 作者资产与规则迁移较大；非程序员改复杂流程的门槛提高 | 资产和语义重接；内置 NavMesh／Animator 任务不能直接替代现有 KCC／Pose |
| 适用目标 | 仍重视统一作者、Agent Document 与既有执行保证 | 规则主要由程序员和 AI 维护，同时保留动作内容编辑 | 有真实图作者需求，希望利用成品编排和调试，愿意承担接入工作 |

“Canvas 只作编辑器、再编译到现有 Program”是 C 的另一种执行选择：可以保留网络／状态保证，但必须限定可编译节点并实现 Frontend、source map 与调试适配。不能把它当成既获得插件全部运行能力、又完全无需改变当前内核的低成本组合。

**8．我的建议与尚未作出的决定。**

建议采用上述共同边界：复杂角色规则以代码表达，动作时间和曲线保留可视化，通用蓝图不作为自研产品目标。这个方向并不要求立即全量删除 BTSMTL，也不要求现在把现有 Program 推翻。

在作者路线选择上，A 能保留最多现有正确成果；B 对程序员与 AI 主导规则维护更直接；C 的优势集中在实际图作者体验和高层行为编排。是否值得迁移，需要对比一条真实动作的编辑过程和完整运行结果，不能仅凭插件功能列表判定。

网络、性能和热更要求不应为某个工具临时绕过；也不能只因为旧系统已经施加了某项约束，就把它永久保留。需要区分真实业务要求和可调整实现。

本轮没有替用户安排其他 change 的实施优先级。现有 56 项作者重构、54 项场景预览计划保持原状；选择路线后再统一改写相应范围、资产迁移和删除清单，避免同一业务长期拥有两套作者数据或两个运行所有者。
